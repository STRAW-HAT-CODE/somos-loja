### Implementation decisions (orchestrator-selected, not extra user requirements)

**Audience and outcome.** A phone visitor coming from a promotional QR should understand the invitation, try its tactile interaction, and see a clear reason to visit. The demo proves usability and direction; it does not issue actual benefits.

**Shared sequence.** Landing invitation -> "Recibir mi postal" -> brief delivery -> "Abrir postal" -> event/benefit details -> optional three discoveries -> completed souvenir. Always offer "Ver invitación" to skip motion. Returning from the collection must not erase the opened letter or consumed-demo state.

**Content truth.** Event name: "Loja 100 % Café Especial". Date, time and venue: "Por confirmar". The source's 50 means approximately brands and farms, not verified specialties; avoid advertising a guaranteed participant count. No fabricated venue links, schedules, testimonials, availability or prizes.

**Visual authority.** Use design/system.md, sourced from absent-apogee/src/styles/global.css: cream paper, indigo, ochre and coffee. Spanish product copy. Self-contained HTML artboards with inline CSS/JS/SVG or raw WebGL, no external URLs/CDNs/fonts. Use Georgia and system-ui as the existing documented fallback stacks. The production website remains untouched.

**A — Correspondencia artesanal.** Branch feat/postal-artesanal. Codex. design/postal-artesanal/01-artesanal.html. An editorial desk composition with a paper-cut courier, tactile envelope flap, a readable postcard and collectible print details. SVG/CSS/JS; no canvas/WebGL dependency. Distinctive crafted composition rather than generic cards.

**B — Cartero en miniatura.** Branch feat/postal-3d. Claude. design/postal-3d/01-miniatura.html. Original baseline: compact raw WebGL, code-built courier, delivery animation and rotation control, with static fallback. Updated by S5: replace the courier with an Alforjita reconstruction based on the user image, using the existing raw WebGL technique (the preliminary img2threejs route was superseded by L22). Preserve the local-only proposal, accessible controls, honest fallback, and performance safeguards. Review model fidelity, runtime size and fallback behavior before treating it as production-ready; this task does not integrate it into the live website.

**C — Entrega cinematográfica.** Branch feat/postal-cine. OpenCode. design/postal-cine/01-cine.html. A camera-like 2.5D scene with foreground/background layers and a courier delivery, followed by the actual HTML postcard. Entirely code-generated, explicitly not a generated video. Replay and skip are supported. This tests the cinematic direction without buying media; a Blender clip can replace the scene after selection.

**Interactions and state.** Each standalone file owns its independent demo state: invitation open, tasting consumed, a set of discovery IDs. Use one state transition function per prototype for these actions; reuse it from all controls rather than separate click-specific implementations. Duplicate discovery activation must not increment progress. Exactly three optional encounters: Origen, Aromas, Preparación, marked as illustrative activities. Completion produces a personal souvenir, not another benefit. No login, camera access, real data capture or network calls.

**Benefit visualization.** A non-scannable ticket/stamp marked "DEMO · SIN VALIDEZ" represents the future personal QR. Do not draw random squares and call them a working QR. A button "Simular canje" changes to "Degustación canjeada" and cannot increase benefits. Explain that production needs controlled issuance and staff validation; a one-use token is not proof of one unique person.

**Accessibility and mobile.** Keyboard-operable buttons, visible focus, accessible names/status updates, readable contrast, no horizontal overflow at 390px, 44px practical tap targets. Respect reduced motion, no compulsory drag, no autoplay audio, no essential text hidden in canvas. The postcard can be reached without waiting for animation. Pause expensive animation when hidden/inactive. No ongoing heavy renderer once the letter is open.

**Artifacts and responsibility.** Parent owns this plan, design/system.md, design/system.html, worktrees, launcher, comparison manifest, Git and functional verification. Workers own only their proposal HTML, design.json, README.md and focused test file. No worker changes existing website files, dependency locks, credentials, this plan, the shared system or another variant. Each proposal README names its technique and what is simulated.

**Testing sequence.** Each worker writes its focused structural/public-document contract test first, runs node --test to observe RED before creating the HTML, then implements and observes GREEN. Tests pin Spanish labels, demo/unknown-data disclosure, inline/no-external-resource contract and script syntax. These are not substitutes for browser checks. Parent runs the public click flow on each variant at desktop/mobile, repeats redemption and discovery actions, resets, tests reduced motion and inspects screenshots plus browser errors. Compare previous production paths structurally: no production source changes are authorized, so no shared-command differential is applicable. Final normalization precedes final checks.

**Production follow-up, not this prototype.** After choosing a direction: integrate it into Astro's existing #evento; approve event facts, capacity and promotion terms; select a person/issuance policy; implement expiring opaque tokens and authenticated staff atomic redemption; define connectivity/manual fallback; test on physical phones and event Wi-Fi; publish only with separate authorization. QR admission and concurrency are high-risk work and deliberately excluded here.

**Delivery and workload.** Forecast: about 300–500 authored lines per standalone alternative, plus tests/docs, and under 300 parent plan/system/comparison lines. Alternatives stay separate instead of becoming one oversized feature diff. Commits are local, coherent and conventional, without AI attribution. No PR strategy is selected or needed for this comparison; ask before any future publishing or combined PR. Runtime/vendor generated bytes, if any, must be distinguished from authored code.
